# Лабораторная работа «Свой DSL»

В проекте есть шесть функций, которые проверяют HTTP-ответы. Они возвращают `true` или `false`. По результату `false` нельзя понять, какое условие нарушено.

Создайте DSL для записи таких проверок. Через него должно быть удобно задать ожидаемый статус, заголовки и содержимое тела ответа. Результат проверки должен содержать все найденные расхождения.

Перепишите функции `check01`–`check06` через свой DSL, сохранив их поведение. Сравните старую и новую реализации на одинаковых данных.

## Подготовка

Вам может помочь лонгрид «Лямбды, inline, лямбды с получателем и свой DSL». Для работы понадобятся функциональные типы, передача лямбд, лямбды с получателем, вложенные получатели и `@DslMarker`.

Работайте в собственной копии [стартового проекта](https://github.com/nikitosion/kfd-dsl-lab). Вместе с заданием предоставляются:

- `app/src/main/kotlin/lesson09/legacy/Checks.kt` — исходные функции `check01`–`check06`;
- `app/src/main/kotlin/lesson09/support/json/Json.kt` — готовый парсер учебного подмножества JSON и типы его результата;
- `app/src/test/kotlin/lesson09/LegacySmokeTest.kt` — начальные тесты исходных проверок;
- тесты готового парсера в `app/src/test/kotlin/lesson09/support/json/JsonParserTest.kt`;
- настроенный запуск тестов через Gradle Wrapper.

Модель ответа, исходные проверки, готовый парсер и начальные тесты не изменяйте. Код DSL разместите в пакете `lesson09.dsl`, свои тесты — в `app/src/test/kotlin/lesson09`.

JSON-парсер писать не нужно. Его входные данные и результат описаны в разделе «Работа с JSON».

Все примеры выполняются на объектах `HttpResponse` в памяти. HTTP-сервер, клиент и сетевые запросы для работы не нужны. Идентификаторы, комментарии и сообщения своего кода пишите на английском. Значения, с которыми сравнивают данные исходные функции, сохраняйте без изменений.

## Основное задание

### Как должен выглядеть результат

Пример использования DSL:

```kotlin
val result = validate(response) {
    status {
        equalTo(200)
    }
    header("Content-Type") {
        startsWith("application/json")
    }
    body {
        json {
            field("id") {
                present()
            }
        }
    }
}
```

Здесь `response` — проверяемый объект. Этот код задаёт три условия: статус равен `200`, хотя бы одно значение заголовка `Content-Type` начинается с `application/json`, а тело содержит JSON-объект с полем `id`.

Если статус равен `200`, заголовок содержит `application/json`, а тело — `{"id":42}`, расхождений нет.

Теперь возьмём ответ со статусом `500`, заголовком `Content-Type: text/plain` и телом `{}`. Проверка должна вернуть три расхождения в таком порядке:

```text
status: expected 200, actual 500
headers.Content-Type: expected prefix application/json, actual [text/plain]
body.json.id: expected present, actual <missing>
```

Ошибка статуса не останавливает проверку заголовка и тела. Проверка JSON выполняется, потому что она явно указана в блоке `body`, даже если `Content-Type` имеет другое значение.

Имена функций и классов можно выбрать самостоятельно. Примеры показывают вложенность блоков и поведение операций. В README приведите аналогичный пример для своего API.

### Шаг 1. Результат проверки

Представьте результат data-классом или sealed-иерархией. Для успешной проверки список расхождений пуст; для неуспешной он содержит найденные нарушения.

Каждое расхождение должно отдельно хранить:

- путь к проверяемой части ответа;
- ожидание;
- фактическое значение или причину, по которой значение недоступно.

Пути в примерах: `status`, `headers.Content-Type`, `body`, `body.json`, `body.json.id`. Можно выбрать другую запись пути, если она однозначно указывает проверяемую часть ответа. Зафиксируйте свою запись в README и проверяйте её в тестах.

Не заменяйте весь результат одним `Boolean` или готовой строкой. Текстовое представление можно получать отдельной функцией. Несовпадение данных с ожиданием не должно приводить к исключению.

Одна неудачная проверка добавляет одно расхождение. Сохраняйте порядок выполнения проверок: сначала операции текущего блока в порядке записи, а при входе во вложенный блок — его операции. Повторные вызовы одной проверки выполняются отдельно; одинаковые расхождения не удаляются.

Для каждого запуска создавайте новый накопитель расхождений. Возвращённый результат должен сохранять свои данные после следующих запусков. Входной HTTP-ответ и его коллекции не изменяйте.

### Шаг 2. Блоки DSL

Создайте отдельные типы получателей для проверки ответа, статуса, значений заголовка, тела, JSON-объекта и его поля. Передавайте настройку каждого блока через лямбду с получателем.

Разделите доступные операции по уровням:

| В каком блоке | Что можно задать |
| --- | --- |
| Ответ | Проверки статуса, выбранного заголовка и тела |
| Статус | Равенство числу |
| Заголовок | Наличие точного значения, совпадение префикса и пользовательскую проверку значения |
| Тело | Отсутствие или пустую строку; наличие непустой строки; проверку JSON |
| JSON-объект | Проверки выбранных полей |
| Поле JSON | Наличие поля, равенство строке, целому числу или логическому значению |

Пометьте типы получателей одной аннотацией с `@DslMarker`. Неявный вызов внешнего блока из внутреннего должен запрещаться компилятором. Например, внутри проверки тела нельзя неявно начать новую проверку статуса ответа.

При этом явное обращение к внешнему получателю через метку должно оставаться возможным. Если входная функция называется `validate`, пример такого обращения — `this@validate.status { ... }`.

Для реализации DSL не подключайте готовые библиотеки проверок, `kotlin-reflect` и обход членов классов. Используйте готовый JSON-парсер из проекта. Ссылки на функции и свойства разрешены.

### Шаг 3. Правила проверки данных

#### Статус и тело

Проверка «тело отсутствует или пустое» проходит для `null` и `""`. Строка из пробелов пустой не считается.

Проверка «тело непустое» проходит для любой строки длиной больше нуля, включая строку из пробелов. Для `null` и `""` она возвращает расхождение.

Разбор JSON выполняется только при вызове соответствующего блока. Проверка непустого тела сама по себе не должна разбирать его содержимое.

#### Заголовки

Имена заголовков сравнивайте без учёта регистра. Если в модели есть несколько ключей, отличающихся только регистром, объедините их значения для проверки.

Значения сравнивайте с учётом регистра. Не обрезайте пробелы и не разбивайте строки по запятой.

Каждая операция над заголовком проходит, если ей удовлетворяет хотя бы одно его значение. Разные операции могут проходить на разных значениях. Например, две проверки точного значения `application/json` и `text/html` проходят для списка из этих двух строк. Одна строка `application/json,text/html` их не заменяет.

Для проверки префикса используйте смысл `String.startsWith`: строка `application/jsonp` начинается с `application/json`. Это правило совместимости с исходными функциями; проверка корректности MIME-типа в работу не входит.

Отсутствующий заголовок и заголовок с пустым списком значений должны давать разные фактические значения в расхождении. Например, `<missing>` и `[]`. Для непустого списка укажите его значения в сообщении; порядок значений из разных ключей, отличающихся регистром, выберите и опишите в README.

#### Пользовательская проверка

Добавьте операцию проверки значения заголовка, которая принимает описание ожидания и функцию типа `(String) -> Boolean`.

Пример:

```kotlin
val result = validate(response) {
    header("X-Trace") {
        satisfies("non-blank value") { value ->
            value.isNotBlank()
        }
    }
}
```

Правило для списка значений то же: достаточно одного значения, для которого предикат вернул `true`. Если заголовка или его значений нет, предикат не вызывается, а операция возвращает одно расхождение.

Покажите в тестах три способа передать одну и ту же проверку: литерал лямбды, переменную функционального типа и ссылку на обычную функцию. Результаты на одинаковых ответах должны совпадать.

В тестах используйте предикаты, которые возвращают результат без исключений и не изменяют проверяемые данные. Обработка исключений из пользовательского предиката в работу не входит.

#### Работа с JSON

Вызовите `parseJsonObject(source)` из пакета `lesson09.support.json`. Он принимает строку и возвращает один из двух результатов:

- `JsonParseResult.Success`: свойство `fields` содержит `Map<String, Any?>` с разобранными полями;
- `JsonParseResult.Failure`: свойство `reason` содержит описание ошибки на английском.

Значения в `fields` имеют тип `String`, `Long`, `Boolean` или равны `null`. Для проверки наличия ключа используйте `containsKey`: обращение по ключу возвращает `null` и для отсутствующего поля, и для поля со значением JSON `null`.

Пример вызова готового парсера:

```kotlin
import lesson09.support.json.JsonParseResult
import lesson09.support.json.parseJsonObject

fun printJsonResult(source: String) {
    when (val result = parseJsonObject(source)) {
        is JsonParseResult.Success -> println(result.fields)
        is JsonParseResult.Failure -> println(result.reason)
    }
}
```

Парсер поддерживает учебное подмножество JSON:

- один объект верхнего уровня, включая `{}`;
- строковые, целочисленные, логические значения и `null`;
- целые числа по записи `-?(0|[1-9][0-9]*)` в диапазоне `Long`;
- экранирования `\"` и `\\` внутри строк;
- пробел, табуляцию, LF и CR между лексемами.

Вложенные объекты, массивы, дроби, другие escape-последовательности, переполнение числа, лишняя запятая, посторонний текст после объекта и неэкранированные символы U+0000…U+001F внутри строки отклоняются. При повторении ключа сохраняется последнее значение.

Если тело равно `null` или парсер не смог его разобрать, добавьте одно расхождение на уровне `body.json` для этого вызова блока `json`. Проверки его полей не выполняйте. Другие проверки ответа продолжайте.

Если объект разобран, выполняйте проверки полей в порядке их записи. Сам выбор поля не создаёт расхождение: его создают операции внутри блока. Для отсутствующего поля проверки наличия и равенства не проходят. Если таких операций несколько, каждая возвращает своё расхождение.

Примеры различий:

| Тело | Проверка поля `id` | Результат |
| --- | --- | --- |
| `{}` | Поле присутствует | Не проходит |
| `{"id":null}` | Поле присутствует | Проходит |
| `{"id":42}` | Значение поля — целое число 42 | Проходит |
| `{"id":"42"}` | Значение поля — целое число 42 | Не проходит |

Проверка равенства учитывает и тип, и значение. Их несовпадение даёт одно расхождение для этой операции.

### Шаг 4. Перепишите исходные проверки

Создайте по одной новой проверке для каждой функции `check01`–`check06`. Новые проверки должны использовать DSL и возвращать его результат. Исходные функции остаются эталоном для сравнения успешности.

Все условия одной строки таблицы должны выполняться одновременно. Дополнительные заголовки и поля JSON не влияют на результат.

| Функция | Когда проверка проходит |
| --- | --- |
| `check01` | Статус 204; тело равно `null` или `""`. |
| `check02` | Статус 200; хотя бы одно значение `Content-Type` начинается с `application/json`; тело не `null` и не пусто. Разбор JSON не выполняется. |
| `check03` | Статус 200; в значениях `Accept` есть точные строки `application/json` и `text/html`. |
| `check04` | Статус 200; тело — допустимый JSON-объект; ключ `id` присутствует, в том числе со значением `null`; `name` — строка `Ivanov`. |
| `check05` | Статус 200; тело — допустимый JSON-объект; `id` — целое число 42; `active` — логическое `true`. |
| `check06` | Статус 422; хотя бы одно значение `Content-Type` начинается с `application/json`; тело — допустимый JSON-объект; `error` — строка `invalid`; `retry` — логическое `false`. |

Не добавляйте новые ограничения к исходным проверкам. Например, `check02` должна пропускать непустое тело с неверным JSON, если статус и заголовок подходят.

## Проверка решения

### Сравнение со старым кодом

Для каждой из шести функций подготовьте ответ, который проходит все её условия. Затем по отдельности нарушьте каждое условие, оставляя остальные выполненными.

На каждом ответе сравните исходную функцию и новую проверку: результат `true` должен соответствовать пустому списку расхождений. Отдельно сравнивайте полный список расхождений с ожидаемым, включая пути, ожидания и факты.

### Пограничные случаи

Обязательные тесты:

- `null`, `""`, `" "` и непустое тело;
- отсутствующий заголовок, пустой список значений и пустая строка внутри непустого списка;
- другое написание имени заголовка по регистру и несколько ключей, отличающихся регистром;
- несколько значений заголовка, включая случай, когда разные проверки проходят на разных значениях;
- различие регистра и внешних пробелов в значениях заголовка;
- корректный и некорректный JSON, отсутствующее поле, JSON `null`, несовпадение типа значения;
- лишние поля JSON и заголовки, которые не должны мешать успешной проверке;
- несколько независимых нарушений в одном ответе с проверкой порядка расхождений;
- ошибка разбора JSON вместе с ошибкой статуса или заголовка: одно расхождение разбора и остальные независимые расхождения;
- два одинаковых вызова проверки, которые дают две записи при неудаче;
- пользовательский предикат в трёх формах передачи;
- сохранность входного ответа и независимость результатов повторных запусков.

Несколько условий можно проверить одним тестом. Число тестов само по себе не оценивается.

Для проверки повторных запусков сохраните блок настройки в переменную. Примените его последовательно к подходящему, неподходящему и снова подходящему ответу. Первый и третий результаты должны быть успешными, второй — содержать ожидаемые расхождения. После всех запусков ранее полученные результаты не должны измениться.

В этих тестах используйте одни и те же настройки проверок и неизменяемые захваченные значения.

## Дополнительные операции — по желанию

Можно добавить проверку диапазона статусов и отдельную проверку равенства поля JSON значению `null`. Для основной части они не требуются и на её оценку не влияют.

Если добавили диапазон, включайте обе границы и проверьте статусы `199`, `200`, `299`, `300` для диапазона `200..299`. Если добавили проверку `null`, она должна проходить для присутствующего поля со значением JSON `null` и не проходить для отсутствующего поля или другого значения.

## Если хочется задачи сложнее: переиспользуемая спецификация

Эта часть необязательна и не влияет на оценку основной работы. Для полной оценки достаточно основной части.

Расширьте DSL так, чтобы набор проверок можно было описать один раз и применять к разным HTTP-ответам.

Пример:

```kotlin
val specification = responseSpec {
    status {
        equalTo(200)
    }
    header("Content-Type") {
        startsWith("application/json")
    }
}

val firstResult = specification.validate(firstResponse)
val secondResult = specification.validate(secondResponse)
```

### Описание и выполнение

Разделите два этапа:

1. `responseSpec { ... }` выполняет блок настройки один раз и сохраняет описание правил. На этом этапе HTTP-ответа ещё нет, проверки значений и пользовательские предикаты не выполняются.
2. `specification.validate(response)` выполняет сохранённые правила для переданного ответа. Каждый вызов создаёт отдельный результат и отдельный накопитель расхождений.

Повторный вызов `validate` не должен заново выполнять исходный блок настройки. Способ хранения правил выберите самостоятельно: это могут быть объекты операций или функции, принимающие данные текущего запуска.

Спецификация не должна сохранять проверяемый ответ или результаты его проверки между вызовами. После создания её набор и порядок правил не меняются.

Все правила основной части сохраняются: порядок расхождений, обработка заголовков, пропуск проверок полей при ошибке JSON и различие отсутствующего поля и `null`.

Основной способ вызова DSL должен оставаться доступным и проходить прежние тесты. Можно реализовать его через создание спецификации и её однократное выполнение.

### Общие наборы правил

Добавьте включение готовой спецификации в другую на уровне ответа:

```kotlin
val commonRules = responseSpec {
    status {
        equalTo(200)
    }
}

val userRules = responseSpec {
    include(commonRules)
    body {
        json {
            field("id") {
                present()
            }
        }
    }
}
```

Включённые правила выполняются на том же ответе и в том месте порядка проверок, где записан `include`. Само включение не выполняет проверки и не создаёт расхождений. Повторное включение добавляет правила ещё раз; одинаковые правила не объединяются автоматически.

Для этой части достаточно включать уже созданные спецификации. Изменение готовых спецификаций, циклические включения и параллельное выполнение не требуются.

### Тесты для спецификации

Добавьте тесты, которые подтверждают:

- блок настройки выполняется один раз при создании спецификации и не выполняется при её последующих запусках;
- пользовательский предикат не вызывается при создании спецификации и вызывается при проверке ответа с подходящим заголовком;
- последовательность «подходящий ответ → неподходящий → подходящий» даёт независимые результаты;
- проверка второго ответа не изменяет ранее возвращённый список расхождений;
- один общий набор правил можно включить в две разные спецификации без переноса ошибок между ними;
- порядок ошибок учитывает место включения, а повторное включение сохраняет повторные проверки.

Для первых двух тестов можно использовать локальные счётчики вызовов. Остальные предикаты проверяйте с неизменными настройками.

В README объясните, что хранится в спецификации, что создаётся при каждом запуске и какие лямбды выполняются сразу, а какие сохраняются. Укажите функциональные типы этих лямбд. Если использовали `inline`, `noinline` или `crossinline`, объясните назначение каждого модификатора в своём коде; добавлять их только ради наличия не требуется.
